不具合修正のPRをレビューしていて、「この追加されたテストは、修正前のコードで本当に落ちていたのだろうか」と手が止まったことはありませんか？

CIがGreenになれば、修正後の状態でテストが通っていることは分かりますが、そのテストが修正前に落ちていたかどうかまでは、すぐにはわかりません。
実は、これを簡単に確かめる方法があります。
Redの状態そのものを、CIがGreenと判定できる形にしてしまえばよいのです。

この記事では、[`gh stack`](https://docs.github.com/ja/pull-requests/reference/stacked-prs-cli-commands)の登場で行いやすくなった、落ちるテストをCIに刻む手法、 **「Red-Green Stacked PR」** について紹介していきます。
なお、この呼び名は本論執筆の便宜上私が考案した名称です。
TDDのRed-Green RefactorとGitHubのStacked PRを組み合わせた造語となっています。
察しのいい方はこの名前だけで何をしたいのか想像できたかもしれませんね😎

## レビュアーが手で確かめていることは何か？

一般的な不具合修正PRには、次の2つが入ります。

1. 不具合を修正する実装コード
2. 再発を検知するテストコード

構成としては自然です。
ただ、レビューする側には小さな不確かさが残ります。
「このテストは、修正前のコードに当てても本当に落ちるのか?」という点です。

テストの書き方が不十分で、修正前のコードでも通ってしまうテストだったとしましょう。
それでも修正コードと一緒に提出されれば、CIはGreenになります。
不具合を再現できていないテストと、再現できているテストが、CIの表示では区別できません。

そのため、影響の大きい不具合や、ロジックが込み入った修正では、レビュアーが手を動かすことになります。

1. PRのブランチをローカルにpullする
2. 修正コードを一度コメントアウト、あるいはコミットの取り消しを行う
3. テストを実行し、期待通り落ちることを確認する
4. 修正コードを戻す
5. もう一度テストを実行し、通ることを確認する

丁寧にやれば確実ではあります。
ただ、確認できるのはその場かぎりで、結果はレビュアーの手元にしか残りません。
PRの数が増えれば、ここがそのままボトルネックになります。
また、忙しいレビュアーがこれを行なってくれるとも限りません。
一見正しそうであれば見逃され、そのまま間違った修正がリリースされてしまうかもしれません。

## プルリクエストを分割し、失敗をCIに刻む

**`test.fails`** は、Vitestが提供するテストの修飾子です[^1]。
これを付けたテストは、失敗したときにPassと判定され、成功してしまったときにFailと判定されます。
成否がそのまま反転します。

この反転を使うと、「今のコードではこのテストは落ちる」という主張を、CIが検証できる形で宣言できます。

:::message
TypeScript/JavaScript, Vitestの例として、`test.fails`を紹介しています。
他の言語やテストフレームワークでも概念上は同じ手法が通用します。
もしお使いのテストフレームワークにこのようなAPIが無かった場合は...コントリビューションチャンスです！！！
きっとみんながこのAPIを求めているはずです。
:::

### 再現テストだけのPRを作る

例として、税込価格を求める処理を考えます。
仕様は、1円未満を切り捨てることです。
ところが実装は四捨五入していて、小数部が0.5以上になる金額でだけ、正しい額より1円多く返します。
税抜105円がその条件にあたります。
税込は115.5円になるため、仕様どおりなら115円、現在の実装では116円です。

この仕様の側をアサーションに書いたPR（PR 1）を作ります。
実装には手を付けません。

```typescript
test.fails("小数部が0.5以上になる場合でも、税込価格は1円未満を切り捨てること", () => {
  expect(toTaxIncluded(105)).toBe(115);
});
```

テスト名も仕様の形にしておきます。
「税込価格が1円多くなる」のように不具合の側を写した名前を付けると、`.fails` を外したPR 2で名前と中身が食い違います。

現在の実装は116を返すため、このテストは落ちます。
`test.fails` が付いているので、CIはGreenになります。

このGreenが意味するのは、修正後にテストが通ったということではありません。
現在の実装に対して、このテストが期待通り落ちたということです。
レビュアーが手元でやっていた3番目の手順が、そのままCIの記録になります。

### 修正PRを上に積む

次に、PR 1のブランチをbaseに指定して、修正PR（PR 2）を作ります。
PR 2でやることは2つです。

- `.fails` を外して通常の `test` に戻す
- 不具合を修正する実装を入れる

```typescript
// .fails を外す。テスト本体はPR 1のまま
test("小数部が0.5以上になる場合でも、税込価格は1円未満を切り捨てること", () => {
  expect(toTaxIncluded(105)).toBe(115);
});
```

PR 2のCIがGreenになれば、さきほど落ちることを確認したのと同じテストが、実装の修正によって通るようになったことになります。
diffには `.fails` が外れた行だけが現れるため、テスト本体が書き換えられていないことも同時に読み取れます。

構造としては次の形になります。

```text
main
└─ PR 1: 再現テストの追加
   │      test.fails(...)
   │      CI ✅ 現在のコードでテストが落ちる
   │
   └─ PR 2: 不具合の修正
          test.fails → test
          + 実装の修正
          CI ✅ 同じテストが通る
```

2つのCI結果を並べれば、Red→Greenの遷移が確認できます。
レビュアーがブランチをcheckoutして修正を外す必要はありません。

再現テストのPRと修正のPRを積み、RedとGreenの両方をCIの履歴に残すことができました！

実際にこの形で作ったPRを公開しています。

- [PR 1: 再現テストの追加](https://github.com/bmthd/red-green-stacked-pr-example/pull/2)
- [PR 2: 不具合の修正](https://github.com/bmthd/red-green-stacked-pr-example/pull/3)

PR 2のFiles changedを開くと、テスト側の差分が `.fails` を外した1行だけであることが確認できます。

## PR 1のGreenが保証していないこと

では、PR 1のGreenは「不具合を正しく再現できている」ことの証明になるでしょうか。
そこまでは言えません。

`test.fails` は、テストが落ちた理由を区別しないためです。
アサーションが期待値と食い違ったのか、テストコード自体がエラーになったのかを見ていません。
実際に試すと、次の2つはどちらもPassになります。

```typescript
test.fails("アサーションの失敗", () => {
  expect(1).toBe(2);
});

test.fails("存在しない関数の呼び出し", () => {
  notDefinedAtAll();
  expect(1).toBe(1);
});
```

```text
 Test Files  1 passed (1)
      Tests  2 expected fail (2)
```

対象の関数名を打ち間違えたテストも、importを書き忘れたテストも、PR 1のCIをGreenにします。
CIが保証するのは「このテストは現在のコードで落ちる」ところまでで、「落ちる理由が対象の不具合である」ことまでは保証しません。

そこはレビュアーが読んで判断する部分として残ります。
ただ、読む対象はPR 1のdiffだけです。
手元に環境を組み直して実装を巻き戻す作業とは、負荷が違います。

## コミットを分けるだけではなぜ足りないのか

今までも、テストと修正のコミットを分けること自体は行われてきました。
1つのPRの中でコミットを2つに分ければ十分ではないか、という反論はもっともです。

```text
commit 1: test: add failing test for bug reproduction
commit 2: fix: resolve logic issue
```

commit 1 を checkout すれば、テストが落ちることは確認できます。
ただし、確認するのは人間です。

各コミットでCIを走らせる設定にしても、事情は変わりません。
commit 1 の時点でCIが走れば、その結果はRedになります。
Redは、テストが意図通り落ちたのか、ビルドが壊れたのか、無関係なテストが巻き添えで落ちたのかを区別しません。
ブランチ保護をかけていれば、マージできない状態のコミットが1つ増えるだけです。

`test.fails` が変えるのは、この点です。
「落ちる」という状態が、CIにとって検証対象の主張になります。
主張である以上、判定した結果がPRのCI履歴として残ります。

## 適用しないケース

では、すべての不具合修正を「Red-Green Stacked PR」にすべきでしょうか。

1つの修正につきPRが2つになるコストは固定でかかるため、タイポや影響範囲の閉じた修正では手続きのほうが重くなります。
再現テストが安定して書けない不具合も対象外です。
これは実行のたびに成否が変わるFlakyなテスト、レースコンディション、特定の環境でだけ起きる表示の崩れなどが該当します。

向いているのは、挙動の因果関係をレビューで強く押さえておきたい、重要または複雑な不具合修正です。

## `gh stack` によるスタックの作成とマージ

以前は、この2段構成を手で組む必要がありました。
PR 1を作り、PR 2のベースブランチにPR 1のブランチを指定し、マージの順番も自分で管理する、という手順です。

`gh stack` は、この部分を引き受けます。
ブランチを下から順に渡すとスタックとして登録され、PRの作成までが1コマンドで済みます。

```bash
# 下から順にブランチをスタックへ登録する
gh stack init test/repro-tax-rounding fix/tax-rounding

# ブランチをpushし、ベースブランチを設定したPRを作る
gh stack submit
```

作られたスタックは、GitHubのPR画面にも表示されます。

![修正PRの画面。CIのチェックが成功し、「Able to merge as a stack」の下にmain、#2、#3が積み上がった形で並び、「Merge stack 2」ボタンが表示されている](/images/red-green-stacked-pr/gh-stack.png)

`main` から積み上がった2つのPRと、CIの状態が同じ画面に並びます。
Red→Greenの遷移を追うために、レビュアーがPRのページを行き来する必要はありません。

マージも、スタックの一番上にあたる修正PRからまとめて行えます。
画面の「Merge stack」が対象にするのは、下に積まれたPRを含めた2つです。
再現テストのPRだけが先に `main` に入り、`test.fails` が取り残される状態を避けられます。

CLIからは `gh stack merge` が同じ操作にあたります。

```bash
gh stack merge
```

どちらの経路でも、スタックに含まれるPRのどれか1つでもマージできなければ、どれもマージされません。

## おわりに

冒頭に挙げた、ブランチをcheckoutして修正をコメントアウトする手順は、確認としては正しいものでした。
問題は、その結果がレビュアーの手元にしか残らないことです。

「Red-Green Stacked PR」として再現と修正を分ければ、同じ確認がCIの履歴になります。
PR 1のGreenが「このテストは現在のコードで落ちる」ことを、PR 2のGreenが「同じテストが修正後に通る」ことを示します。

実のところ、この運用はStacked PRという言葉が広まる前から手元で続けていたものです。
PR BのbaseブランチにPR Aを指定すれば手動でも組めますが、順番にマージする手間のほうはツールが引き受けてくれるようになりました。

落ちる理由が対象の不具合かどうかは、依然としてレビュアーが読んで判断する部分です。
ここを機械に渡す方法は、まだ思いついていません。
AIやツールが便利になっても、我々が必要でなくなるのはまだまだ先かもしれませんね。

[^1]: Jestでは `test.failing`（jest-circusランナーのみ）、Playwrightでは `test.fail()` が同じ役割を持ちます。なお、Vitestは4.1以降、`fails` を付けたテストをテストサマリーに集計します。
