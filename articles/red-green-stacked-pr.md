不具合修正のコードレビューにおいて、「この追加されたテストは、修正前のコードで本当に落ちていたのだろうか？」と疑問に思ったことはないでしょうか。

通常、1つのPRの中に「不具合を直すコード」と「回帰テスト（再現テスト）」がセットで入ってきます。CIがGreenになれば「修正後の状態でテストが通っている」ことは確認できますが、「そのテストが修正前に正しく不具合を検出できていたか」まではCIの結果だけでは分かりません。

この記事では、Vitestの `test.fails` とStacked PR（PRの積み重ね）を組み合わせることで、**「修正前は確実に失敗する」ことと「修正によって成功するようになった」ことの両方をCIの結果だけで検証・可視化する運用**について紹介します。

---

## 従来の不具合修正PRが抱える確認コスト

一般的な不具合修正フローでは、1つのPRに以下の2点が含まれます。

1. 不具合を修正する実装コード
2. 不具合の発生を防ぐ（再発を検知する）テストコード

この構成自体は自然ですが、レビューする立場からすると1つ小さな不確かさが残ります。それは、**「このテストは修正前のコードに適用したとき、本当にRed（失敗）になるのか？」** という点です。

もしテストの書き方が不十分で、修正前のコードに対してもパスしてしまうようなテスト（＝不具合を再現できていないテスト）だったとしても、修正コードと一緒に提出されればCIは問題なくGreenになってしまいます。

そのため、重要な不具合やロジックが複雑な修正では、レビュアーが以下のような手作業を行うことがありました。

1. PRのブランチをローカルに `git checkout` する
2. 修正コードを手動で一度コメントアウト（または巻き戻し）する
3. テストを実行し、**期待通り失敗すること**を確認する
4. 修正コードを元に戻す
5. 再度テストを実行し、**成功すること**を確認する

この確認を丁寧に行えば確実ではありますが、レビュアーへの負荷が高く、PRの数が増えるにつれてボトルネックになりやすいのが課題でした。

## `test.fails` と PR分離によるアプローチ

この「手作業による確認」を、**PRの構造とCIの検証**に委譲するのが今回の手法です。

具体的には、不具合修正を以下の2段階のPRに分けて提出します。

1. **PR 1: 不具合再現テストの追加**（`test.fails` を使用）
2. **PR 2: 不具合の修正とテストの正常化**（PR 1の上にstackする）

それぞれの役割を詳しく見ていきます。

### Step 1. 再現テストのみを `test.fails` でPRにする

Vitestには `test.fails` という機能があります。これは「テストが失敗したときに成功（Pass）扱いとし、逆にテストが成功してしまった場合に失敗（Fail）扱いとする」アプローチです。

まず、不具合を再現するテストコードだけを書いたPR（PR 1）を作成します。

```typescript
// 再現テストを追加（この時点では修正コードは入れない）
test.fails("特定の条件下で計算結果が歪む不具合の再現", () => {
  const actual = calculateAmount(config);
  expect(actual).toBe(expectedValue);
});
```

現在のコードベース（未修正の状態）ではこのテストは本来失敗しますが、`test.fails` を指定しているため、**CI上ではGreen（成功）** になります。

このCIがGreenになることで、人間の主観ではなくCIシステムによって、**「現在の実装では、このテストが期待通り失敗する（＝不具合を正しく再現できている）」** ことが客観的に確認できます。

### Step 2. 修正PRを上にstackする

次に、PR 1をベース（親）にして、修正PR（PR 2）を作成します。

このPR 2では、以下の変更を行います。

* `test.fails` の `.fails` を外し、通常の `test` に戻す
* 不具合を修正する実装コードを追加する

```typescript
// `.fails` を外して通常のテストにする
test("特定の条件下で計算結果が歪む不具合の再現", () => {
  const actual = calculateAmount(config);
  expect(actual).toBe(expectedValue);
});
```

PR 2のCIを実行すると、**「先ほど確実に失敗していた同じテストが、修正実装によって成功するようになった」** ことが確認できます。

### 全体の構造イメージ

```text
main
└─ PR 1: 不具合再現テスト
   │      test.fails(...)
   │      CI ✅（現在のコードで「テストが失敗すること」を確認）
   │
   └─ PR 2: 不具合修正実装
          test.fails → test
          + 実装コードの修正
          CI ✅（修正によって「同じテストが成功すること」を確認）
```

この2つのPRのCI結果を見るだけで、レビュアーはローカルにコードをpullして修正を外すといった作業を一切せずとも、**Red → Green の遷移をCIの履歴だけで確認**できます。

## 単なるコミット分割との違い

「それなら1つのPRの中でコミットを2つに分ければ十分では？」と思われるかもしれません。

```text
commit 1: test: add failing test for bug reproduction
commit 2: fix: resolve logic issue
```

たしかにコミットを分けるだけでも、手動で `commit 1` を checkout すれば落ちることは確認できます。

しかし、その確認はどこまでも**人間が手動で行うこと**が前提になります。CIサーバーは通常、PRの最新のコミット（Merge Commit含む）に対してしかビルドやテストを実行しないため、`commit 1` の時点で本当にテストが落ちていたのかはCI上に残りません。

`test.fails` を使ってPR単位で分離することにより、**「Redの状態」そのものをCIで検証・保存可能な成果物としてPRにする** ことができる点が、単なるコミット分割との本質的な違いです。

## Stacked PRとの歴史的文脈

少し運用面の補足です。

私自身、この「再現テストの分離」というアプローチ自体は、いわゆる「Stacked PR」という用語や専用ツールが一般的になる前から行っていました。当時は手動でPR Aを作成し、PR Aのブランチから生やしたPR BのbaseブランチをPR Aに指定する、という運用で実現していました。

したがって、「Stacked PRという仕組みから思いついた手法」というよりは、**「もともとやっていた Red→Green の分離運用が、近年のStacked PRツール（GhstackやGraphite、あるいはGitHub CLI等）の進化によって非常に扱いやすくなった」** という関係性に近いです。

以前はベースブランチを意識しながら順番にマージする手間がありましたが、現在はツール側のサポートにより、スタックされたPRの作成や更新、最終的なマージ操作のハードルが大きく下がっています。

## デメリットと適用しないケース

この運用は非常に有用ですが、万能な銀の弾丸ではありません。チームや修正の規模に応じて適宜使い分けることが重要です。

* **PRの数が増える**
  1つの修正に対して2つのPRを作成・管理するため、単純にPRの管理コストが増えます。
* **軽微な修正には過剰**
  タイポの修正や、影響範囲がごく閉じた軽微なバグ修正でこれを行うのは過剰になりがちです。
* **一時的に `test.fails` が入る問題**
  何らかの事情で PR 1 だけが先行して `main` にマージされる運用の場合、`main` ブランチに `test.fails` が残ってしまいます（修正されたタイミングで逆にCIが落ちる原因になるため、基本的にスタック全体をまとめてマージするか、同時にマージする運用が必要です）。
* **Flakyなテスト（不安定なテスト）との相性が悪い**
  実行タイミングによって成功/失敗が変わる非決定的なテストの場合、`test.fails` のCI結果も不安定になり、混乱を招きます。
* **テストで再現しづらい不具合**
  タイミング依存のレースコンディションや、特定環境でのみ発生するUIの崩れなど、自動テストに落とし込みにくい不具合には向きません。

「すべてのバグ修正で必ず適用すべき」というルールにするのではなく、**「挙動の因果関係をレビュー上で強く保証したい重要・複雑なバグ修正」** において選択肢として持つのが現実的です。

## まとめ

不具合修正のレビューにおいて真に確かめたいのは、**同じテストケースに対して「修正前は落ちる」「修正後は通る」という2つの状態が成立しているか** です。

通常のPR作成では、CI上には「修正後に通った」という片方の状態しか現れません。

`test.fails` とStacked PRを活用して「再現」と「修正」を構造的に分離することで、

* **修正前：** `test.fails` がCIでPassする ＝ 不具合を正しく検出できていることの検証
* **修正後：** 通常の `test` がCIでPassする ＝ 修正によって不具合が解消したことの検証

という両方の状態を、レビュアーの手作業に頼らずCIの成果物として残すことができます。

「レビュー時の動作確認の手間を、コードやPRの構造とCIへ寄せる」という思考の引き出しの一つとして、参考になれば幸いです。
